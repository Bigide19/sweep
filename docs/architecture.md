# [설계] Sweep 구조와 판단 근거

Sweep이 왜 이런 구조인지 설명하는 문서입니다. 룰 목록은 `rules.md`에 있습니다.

## 문제

빌드 산출물과 캐시를 손으로 정리할 때마다 같은 판단을 반복합니다. 후보를 찾고, 패키지가 배포한 코드인지 내가 빌드한 산출물인지 가리고, 그 캐시를 지금 쓰는 프로젝트가 있는지 확인하고, 작업 중인 프로젝트인지 봅니다. 네 단계 모두 규칙으로 굳힐 수 있는데 매번 사람이 했습니다.

특히 이름만 보고 지우면 프로젝트가 깨지는 함정이 있습니다. `node_modules/next/dist/build`와 `packages/Stub.System.Data.SQLite.../build`는 패키지가 배포한 실제 코드입니다. `find -name build -delete` 같은 명령은 이걸 구분하지 못합니다.

## 판정: 우선순위 경쟁

룰은 절대경로에 대한 정규식이고, 각자 우선순위를 갖습니다. 여러 룰이 맞으면 우선순위가 높은 쪽이 이기고, 같으면 deny가 이깁니다.

```
110  allow  rn-native-build     /node_modules/(@[^/]+/)?[^/]+/(android|ios)/build$
 50  deny   node-package-code   /node_modules/.+/(build|bin|obj|lib|dist)$
```

`node_modules` 안의 `build`는 대체로 패키지 코드라 금지해야 하지만, 그중 `android/build`만은 React Native 라이브러리를 소스에서 빌드한 산출물이라 지워야 합니다. 넓은 금지를 아래에 깔고 좁은 예외를 위에 얹으면 이 관계가 그대로 표현됩니다.

이 구조를 고른 이유는 확장 방식 때문입니다. 새 예외가 생겨도 기존 룰을 건드리지 않고 높은 우선순위 룰 하나만 추가하면 됩니다. 조건을 룰 안에 중첩시키는 방식이라면 예외마다 기존 정규식을 고쳐야 하고, 그때마다 이미 통과했던 케이스가 깨질 위험을 다시 검증해야 합니다.

## 탐색: 세 가지 모드

스캔 시작점마다 훑는 방식이 다릅니다. 같은 방식으로 다 훑으면 느리거나 부정확합니다.

| 모드 | 방식 | 쓰는 곳 |
|---|---|---|
| `walk` | 재귀로 내려가며 관심 디렉터리 이름을 만날 때마다 판정 | `~/Projects` |
| `children` | 바로 아래 자식만 판정 | `~/Library/Caches`, `~/.gradle/caches` |
| `leaf` | 경로 자체가 후보 | `~/.npm/_cacache` |

`children`이 따로 있는 이유는 `~/Library/Caches`에 항목이 222개나 되고 성격이 제각각이기 때문입니다. 여기서는 화이트리스트에 없는 항목을 "성격 미확인"으로 표시만 하고 삭제를 막습니다. 반대로 `walk`에서는 룰에 안 걸리면 그냥 지나쳐 더 깊이 내려갑니다.

### node_modules 처리

`walk`에서 판정이 나면 그 아래로는 내려가지 않습니다. allow면 통째로 지울 대상이라 안을 볼 이유가 없고, deny면 건드리지 않을 영역이기 때문입니다.

`node_modules`는 예외입니다. 맨 바깥 `node_modules`는 그 자체로 후보지만(`node-modules` 룰) allow 판정이 나도 안으로 계속 내려갑니다. 활성 프로젝트라 통째로는 못 지울 때도 RN 라이브러리의 `android/build`는 따로 지울 수 있어야 하기 때문입니다. 이렇게 하면 바깥과 안쪽 후보가 겹칩니다. 그래서 정리 가능 합계와 선택 합계, 삭제 대상을 만들 때 `Candidate.withoutNested`로 다른 후보 안에 든 후보를 뺍니다.

안을 전부 훑으면 패키지가 수천 개라 느립니다. 그래서 `node_modules`를 만나면 깊이 한계를 5로 짧게 잡아 패키지 바로 아래 몇 단만 봅니다. `@scope/pkg/android/build`가 4단이라 5가 필요합니다. 중첩 `node_modules`를 만나면 깊이가 다시 5로 리셋되므로 `expo/node_modules/expo-constants/android/build`처럼 깊게 박힌 것도 찾아냅니다.

크기는 `du`를 부르지 않고 walk 중에 `totalFileAllocatedSize`를 더해서 셉니다. 링크 수가 2 이상인 파일만 inode를 확인합니다. 같은 파일이 후보 안에 두 번 나오면 du처럼 한 번만 세고 링크 일부가 후보 밖에 있으면 `sharedBytes`로 따로 모읍니다. 지워도 그만큼은 디스크가 비지 않기 때문입니다. pnpm 프로젝트의 `node_modules`가 스토어와 이렇게 파일을 공유합니다. APFS clone은 파일마다 확인할 값싼 방법이 없어서 다루지 않습니다. 후보별로 독립이라 CPU 코어 수만큼 병렬로 돌립니다. 실측으로 후보 190개, 40GB 규모에서 35초가 걸립니다.

## 방어: 룰과 안전장치의 분담

룰은 경로 모양만 봅니다. `build`가 산출물인지 사람이 쓴 파일인지는 경로로 알 수 없습니다. 그래서 룰이 allow로 판정한 뒤에도 아래 검사를 통과해야 삭제 후보가 됩니다. git으로 확인하지 못한 경우는 통과시키지 않습니다. 확인을 못 했다는 건 안전하다는 뜻이 아니기 때문입니다.

| 검사 | 판단 근거 | 막는 사례 |
|---|---|---|
| git 추적 | `git ls-files`에 걸리면 소스 | 설치 스크립트를 `build/`에 두고 커밋한 경우 |
| 커밋 안 한 변경 | `git status --porcelain` | 작업 중인 파일이 후보 안에 있는 경우 |
| 툴체인 소유자 | `gradle-wrapper.properties` 역추적 | Gradle 8.14.3을 쓰는 프로젝트가 있음 |
| 실행 중 프로세스 | 실행 파일 이름 정확 비교 | WebStorm 실행 중에 JetBrains 캐시 |
| 프로젝트 활성도 | 마지막 커밋 경과일 | 최근 커밋 30일 이내면 재빌드 부담 경고 |
| 작업 중인 프로젝트 | 프로세스의 작업 폴더(libproc) | 개발 서버나 에이전트 세션이 쓰는 중인 `node_modules`와 `build` |
| 화이트리스트 | 룰 매칭 실패 | 성격 미확인 앱 캐시 |
| 실행 중인 Sweep | 실행 파일 경로가 후보 안에 있음 | 개발 빌드가 자기 `.build`를 지우는 경우 |
| SDK 저장소 | 저장소 안의 표식 파일 (`Library/Homebrew`, `emsdk.py` 등) | Homebrew `.gitignore`가 설치한 프로그램 전체를 무시해서 산출물로 보이는 경우 |
| git 확인 실패 | git 종료 코드, `xcode-select -p` | 명령줄 도구가 없는 맥에서 추적 여부를 모르는 채 통과하는 경우 |
| 저장소 밖 | 상위에 `.git` 없음 (프로젝트 산출물만) | 검사 폴더에 섞인 압축 푼 SDK의 `bin`이 미리 체크되는 경우. 막지 않고 기본 선택만 뺍니다 |

실제로 걸렀던 사례가 이 분담을 잘 보여줍니다. 어떤 Electron 프로젝트는 NSIS 설치 스크립트를 `build/`에 두고 커밋해 씁니다. 룰은 `generic-build`로 보고 allow를 냈지만 git 추적 검사가 막았습니다. 룰만으로 걸러내려면 "설치 스크립트가 든 build는 예외"라는 룰을 손으로 추가해야 하는데, 그런 예외는 프로젝트마다 다르고 미리 알 수 없습니다.

### 프로세스 잠금의 매칭 기준

처음에는 `ps -Ao command=` 출력 전체에 부분 문자열 검색을 걸었습니다. 오탐이 났습니다. `/opt/homebrew/bin/node`가 `brew`에 걸리고, 커맨드라인 인수에 든 경로가 `JetBrains`에 걸렸습니다.

지금은 두 가지를 나눠 씁니다. `lockProcesses`는 실행 파일 이름과 정확히 비교하고, `lockCommands`는 커맨드라인 전체를 부분 문자열로 봅니다. Gradle 데몬처럼 실행 파일이 `java`이고 인수에만 이름이 드러나는 경우에만 후자를 씁니다.

둘 다 도구 단위 판단입니다. "Xcode가 떠 있으면 DerivedData를 막는다"는 맞지만 `node`나 `claude`가 떠 있다고 모든 `node_modules`를 막을 수는 없습니다. 그래서 프로젝트 산출물은 이름 대신 프로세스의 작업 폴더를 봅니다. libproc으로 같은 사용자 프로세스의 작업 폴더를 읽고, 그 폴더가 후보의 프로젝트 안이거나 검사 폴더보다 깊은 상위 폴더면 막습니다. 작업 폴더가 다른 곳이어도 커맨드라인에 프로젝트 경로가 들어 있으면 막습니다. 다른 사용자 프로세스를 못 읽는 건 정상이라 건너뛰고 목록 자체를 못 받았을 때만 막습니다. 표시 이름은 argv[0]에서 가져옵니다. Claude Code CLI는 실행 파일이 버전 번호로 설치돼서 실행 파일 이름으로는 `2.1.x`만 보입니다.

## 삭제 정책

휴지통을 거치지 않고 바로 지웁니다. 휴지통에 넣으면 디스크 점유가 그대로라 목적에 어긋납니다. 되돌릴 방법은 재빌드이므로, 각 후보에 재생성 비용을 표시해서 지우기 전에 판단할 수 있게 합니다.

앱은 몇 시간 전 스캔 결과로 지우기도 합니다. 그 사이 그 프로젝트에서 개발 서버를 띄웠을 수 있어서 프로젝트 산출물은 지우기 직전에 작업 중인 프로세스를 다시 봅니다.

`Sweeper.isSafePath`가 마지막 확인입니다. 홈 디렉터리 안이고 최소 두 단계는 깊어야 하며, `..`이 섞인 경로는 거부합니다. 룰이 잘못돼서 `~`나 `~/Projects`가 넘어오는 사고를 막는 장치입니다.

지울 항목은 먼저 `~/Library/Application Support/Sweep/Deleting` 아래로 이름을 바꿔 옮긴 뒤 지웁니다. `removeItem`은 파일을 하나씩 지우다 막히면 그 자리에서 멈춥니다. 보안 프로그램이 파일 하나만 막아도 캐시가 반쯤 지워진 채 남고, 도구는 그 캐시를 믿고 사용하다가 깨집니다. 같은 볼륨 안에서 이름을 바꾸면 한 번에 끝나므로 원래 경로는 온전히 사라지고, 도구는 캐시를 처음부터 다시 만듭니다. 대기 폴더는 후보 옆에 두지 않았습니다. 저장소 안에 남은 조각이 git에서 추적하지 않는 파일로 보이지 않게 하려는 것입니다. `FileManager.moveItem`은 볼륨이 다르면 복사로 바뀌어서 사용하지 않고 `rename`을 직접 부릅니다. 볼륨이 달라 옮기지 못하면 그 자리에서 지웁니다.

이력은 항목 하나를 끝낼 때마다 바로 남깁니다. 삭제 전후의 남은 공간도 재서 회수량과 크게 어긋나면 함께 보여줍니다. 하드링크 공유처럼 지운 크기만큼 비지 않는 경우를 알아채려는 것이고 다른 프로그램의 쓰기도 섞이므로 참고값으로만 씁니다. 일부만 지워진 항목은 실제로 비운 용량과 막힌 파일 이름을 함께 기록합니다.

## 지우지 않는 큰 항목

디스크를 가장 크게 차지하는 건 다시 만들 수 있는 산출물이 아닌 경우가 많습니다. VM 이미지, Docker 디스크 이미지, 쓸 수 없게 된 시뮬레이터, 로컬 스냅샷이 그렇습니다. 이것들은 후보(`Candidate`)로 다루지 않고 `Insight`로 따로 모읍니다.

지우는 방법이 달라서 후보와 나눴습니다. 후보는 경로를 통째로 지우고 이력에 크기를 남깁니다. VM 이미지나 `Docker.raw`를 경로째 지우면 그 안의 데이터를 모두 잃습니다. 줄이는 방법은 그 앱 안의 기능이거나 도구가 제공하는 명령입니다. 그래서 크기와 줄이는 방법만 보여주고 도구에 정리 명령이 있을 때만 그 명령을 실행합니다(`ToolAction`).

| 항목 | 실행하는 명령 | 실행 조건 |
|---|---|---|
| Docker 디스크 이미지 | `docker builder prune -f` | Docker가 이미 켜져 있을 때만 |
| 쓸 수 없는 시뮬레이터 | `xcrun simctl delete unavailable` | Xcode가 설치돼 있을 때만 |
| VM, Xcode 아카이브, 휴지통, 로컬 스냅샷 | 없음 | 보여주기만 합니다 |

Docker를 켜지 않는 데는 이유가 있습니다. 켜면 재시작 정책이 걸린 컨테이너가 함께 올라옵니다. 이미지와 볼륨 정리도 넣지 않았습니다. 무엇을 다시 받아야 하는지는 사용자만 알기 때문입니다. 외부 명령은 데몬이 멈춰 있으면 끝나지 않을 수 있어서 모두 타임아웃을 두고 GUI 앱의 짧은 PATH 대신 절대 경로로 부릅니다.

다운로드 폴더는 CLI에서 `--downloads`를 줄 때만 봅니다. macOS가 보호하는 폴더라 읽으면 권한 창이 뜹니다. 같은 이유로 메뉴바 앱은 다른 앱의 `~/Library/Containers`(Docker 디스크 이미지, UTM)와 휴지통을 읽지 않습니다. 앱에서 Docker 항목은 Docker가 켜져 있을 때 CLI로 알아낸 정보만 보여줍니다.

## 경계

Sweep이 하지 않는 일입니다.

- **파일 단위 삭제를 하지 않습니다.** `libreactnative.so` 같은 파일만 골라 지우면 Gradle이 태스크를 up-to-date로 판단해 빌드를 건너뛰고 링크 에러가 납니다. 디렉터리 단위로만 다룹니다.
- **성격을 모르는 캐시를 지우지 않습니다.** `~/Library/Caches`의 미확인 항목은 크기만 보여줍니다. 앱별 캐시는 실제 데이터를 담는 경우가 있어 화이트리스트 없이 지울 수 없습니다.
- **자동으로 지우지 않습니다.** 주기 실행은 스캔과 알림까지만 합니다. 삭제는 항상 사람이 고르고 확인 단계를 한 번 더 거칩니다. 도구 정리 명령도 같은 확인 단계를 거칩니다.
- **저용량 알림은 경계를 넘을 때 한 번만 보냅니다.** 남은 공간이 10%나 10GB 아래로 내려가면 알리고 15%와 15GB 위로 회복해야 다음 알림을 준비합니다. 큰 디스크는 10%가 수백 GB라 비율만 보면 늦게 알립니다. 알렸다는 상태를 저장하지 않으면 이미 부족한 맥에서 앱을 켤 때마다 알림이 갑니다.
